# School Manager: карта повного керування через MCP

> Це початковий знімок до розширення MCP: статуси й 11 команд нижче описують базовий стан. Актуальна реалізація містить **93 команди**: [можливості, виключення та перевірки](mcp-implementation.md), [точний каталог](mcp-tools.json). П'ять виключених користувачем напрямів не реалізовуються; пропозиції аудиту не є чинною вимогою змінювати програму.

Аудит вихідного коду станом на **23 жовтня 2026 року**. Мета — виконувати повсякденні операції School Manager голосом або текстом у Codex. Збірки `.exe`, інсталятори й публікацію виконує інший чат через GitHub Actions.

Перевірено 10 основних екранів, усі 18 файлів HTTP-роутерів, моделі даних, планувальники, файлове сховище, інтеграції та desktop-інтерфейс. Знайдено **131 оголошений HTTP-маршрут, 129 обробників, 20 публічних методів native-інтерфейсу та 11 команд MCP**. Два маршрути — дублікати адрес журналу з кінцевим `/`. Службові `/health` і `/api/startup` у `backend/main.py` рахуються окремо. Кількість адрес не є кількістю користувацьких можливостей.

Повний технічний перелік адрес, параметрів, файлів і рядків: [mcp-api-inventory.json](mcp-api-inventory.json).

Це аудит реалізації, а не перевірка всіх дій у робочих акаунтах. Під час аудиту не надсилалися повідомлення, не змінювалися робочі дані або налаштування. Живий виклик MCP `get_status` пройшов через Codex, але повернув відсутність сумісного API у запущеній версії School Manager. Команди MCP завантажені в чат; робочому застосунку ще потрібне оновлення backend.

## Статуси

- **MCP** — команда вже написана у `integrations/codex_mcp/server.py`; потрібні підключений сервер і сумісний backend. Створення/редагування раніше перевірено на окремій тестовій базі.
- **API** — операція є у застосунку; потрібно додати MCP-команду, розпізнавання цільового запису, перевірку параметрів/результату та тести.
- **Доробка** — самого MCP недостатньо: треба змінити програму, модель даних або зв'язок із desktop-процесом.
- **Участь користувача** — MCP може розпочати процес і показувати стан; авторизація або системна дія виконується користувачем.

Назви майбутніх команд нижче — пропозиції, а не вже доступні інструменти.

У таблицях **121 сценарний пункт**: 9 уже охоплені 11 командами MCP, 83 мають основу в наявному API, 25 потребують доробки програми, 4 включають інтерактивний крок користувача. Частина пунктів об'єднує споріднені дії; це карта обсягу, а не відсоток завершення розробки.

Зараз історія ручних розсилок — у `localStorage` інтерфейсу, файли історії — в IndexedDB. MCP не читає їх через наявний API. Загальний журнал подій не замінює історію доставки по кожному одержувачу. Складені розсилки потребують постійних ключів операцій, щоб повтор після тайм-ауту не дублював повідомлення.

Публічний запит створення не має довільної дати `send_at`. `scheduled_target_at` — обчислений результат Telegram-планування. `_next_target_datetime` використовує локальний час ОС, тому потрібна явна робота з поясом/DST. Захист створення від подвійного натискання — fingerprint на **15 секунд у пам'яті**, а не надійний ключ після перезапуску.

| R11 | Звірити непідтверджену доставку з Telegram без повторного надсилання | Доробка | Внутрішнє reconciliation є; потрібна окрема зовнішня операція |

`/parents-report/preview` повертає **контекст заняття, не фінальний AI-текст**, і може оновлювати дані/знімок після Logika. `/send` генерує текст та надсилає в одному сценарії. Отже, «покажи готовий звіт перед відправленням» потребує доробки.

Зберегти перевірку конкретної дати, часу, групи, викладача й відвідування. MCP не повинен обходити ці правила або ототожнювати `success`, `sending`, `uncertain`, `error`, `manual_required`. Поточний аудит не перечитує Telegram-історію й не відновлює відсутню історію змін розкладу. Порожня вибірка не доводить успіх.

## Що доробити для повного щоденного керування

1. **Адресати:** батьківський/учнівський чат, навчальна група, псевдоніми; при однакових назвах уточнювати ціль.
2. **Точні дати розсилок:** `send_at`, часові пояси/DST, одноразові/повторювані правила. Довільну дату не підміняти найближчим днем тижня.
3. **Збережені чернетки повідомлень і звітів:** відправляти підготовлений текст із визначеними адресатами/файлами, не генерувати новий текст під час відправки.
4. **Постійний журнал операцій:** UUID, стан кожного адресата, відновлення після тайм-ауту/перезапуску без дублів.
5. **Результати Telegram:** розрізняти локальне збереження, постановку в Telegram, відправлення, помилку й невизначений стан; перевіряти скасування у Telegram.
6. **Редагування:** явний стан замість toggle, збереження непросимих полів/вкладень, контроль конкурентних змін.
7. **Історія:** ручні розсилки на сервері, фільтри/пагінація журналів, попередні промпти та знімки історичного розкладу.
8. **Узгодження розкладу й календаря:** явні зв'язки; окремі входження серій і нагадування на кожне входження.
9. **Desktop-міст:** навігація, вікно, віджети й системні діалоги з правильним виконанням у GUI.
10. **Тривалі операції:** ID операції, стан/прогрес/результат для синхронізації, імпорту, AI та розсилок. Тайм-аут MCP не запускає другу таку саму дію.
11. **Резервування й lifecycle:** узгоджені копії, повний архів ресурсів, безпечне відновлення/перезапуск.

Для читання, чернеток і звичайного редагування не потрібне зайве підтвердження кожного кроку. Прямий запит користувача з визначеними чатами, текстом/завданням і часом задає дозволений обсяг. Уточнення потрібне за неоднозначності адресата/дії або виходу за запит. Аналіз проблемних звітів сам по собі не є командою їх відправити.

## Порядок реалізації

1. **Спільна основа:** адресати, точні дати, ключі операцій, чернетки, результати та контроль змін.
2. **Найпотрібніші дії:** текстові шаблони → промпти звітів → разові й повторювані повідомлення батькам/учням.
3. **Звіти й розклад:** генерація чернеток, відправлення/повторення, відвідування, перенесення, прив'язки, курси та імпорт/експорт.
4. **Календар та інтеграції:** решта Task API, Google, Logika, файли, серії.
5. **Desktop і обслуговування:** віджети, навігація, вікно, журнали, резервування, lifecycle.

Для кожного сценарію: перевірити вхідні дані → виконати через служби програми → перечитати фактичний стан → повернути конкретний результат. Реальні відправки перевіряти тільки в явно дозволених тестових чатах; більшість логіки перевіряється на окремій базі з підміненими зовнішніми сервісами.

Попередня оцінка покриття 20–25% була приблизною. **11 MCP-команд / 131 маршрут не є відсотком готовності:** адреси мають різний зміст, одна дія може поєднувати кілька маршрутів. Прогрес слід вимірювати реалізованими сценаріями таблиць та їх перевіркою.

## Межі та голосовий режим

Можна реалізувати керування всіма повсякденними можливостями School Manager, додавши описані відсутні операції. Це не охоплює всі дії зовнішніх платформ: керування учасниками Telegram, довільною LMS або оплатами в застосунку не реалізовано. Вхід у Google/Telegram/Logika, надання нових прав і системне встановлення можуть потребувати користувача.

Для голосу й тексту використовується один MCP. Окремий розпізнавач мовлення у School Manager не потрібний. Голос/диктування Codex передає завдання, MCP виконує конкретні дії; доступність голосового режиму залежить від клієнта, акаунта та налаштувань. Повний голосовий сценарій на цьому ПК ще потрібно перевірити після оновлення School Manager.

Офіційна документація OpenAI: [MCP](https://learn.chatgpt.com/docs/extend/mcp), [Voice](https://learn.chatgpt.com/docs/features/voice). Голос у Codex використовує контекст і дозволи завдання; MCP надає інструменти й результати.

Оновлення основної програми не встановлює MCP на комп'ютери інших користувачів автоматично. Його пакування, залежності й реєстрація потрібні в плані розповсюдження; вони відокремлені від GitHub Actions-збірки backend/desktop.
