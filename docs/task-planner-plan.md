# Задачник і календар: план реалізації

Статус: реалізовано у вихідному коді; локальні перевірки завершено. Докази й межі перевірки зовнішніх сервісів: `docs/task-planner-verification.md`. EXE не збирався. Нижче збережено погоджений план і наступні напрямки розвитку.

## Мета та сценарії

Окрема вкладка «Задачник» для роботи викладача: майбутні уроки, заміни, підготовка до уроків і заходів. Інтерфейс розвиваємо малими кроками після перегляду кожної робочої версії.

Підготовлено підключення особистого Google Календаря, Telegram-нагадування в «Збережені повідомлення» та компактне вікно задач. Реальний Google-вхід перевіряється після створення OAuth-клієнта; реальні повідомлення в Telegram під час розробки не надсилалися.

Основні сценарії:

- Побачити заняття тижня, вибрати урок і додати пов’язану задачу «Підготувати матеріали» на попередній день.
- Додати разову заміну з датою, часом, групою та короткою приміткою.
- Запланувати підготовку до заходу; згодом додати чекліст.
- Перенести задачу на інший день і бачити, чи зміна вже потрапила в Google.
- Відзначити підготовку виконаною, залишивши сам урок у календарі.
- Пізніше отримати особисте нагадування в Telegram у вибраний час.

Дизайн: компактний робочий інтерфейс у поточній темній палітрі School Manager, з невеликими відступами й зрозумілими станами. Візуальні рішення першого макета є пропозиціями, їх можна змінювати під час розробки.

## Перший варіант екрана

У меню після «Звіт батькам» додати «Задачник». Новий маршрут `/tasks`, решта пунктів зберігають назви й адреси.

```text
Задачник                       Google: синхронізовано    [+ Додати]
[Сьогодні] [‹] Вересень 2026 [›]   [Тиждень | Місяць | Список]
[Усі типи] [Усі джерела] [Пошук…]             [Показати виконані]
┌─────────────────────────────────────────┬───────────────────────┐
│ Календар: уроки, заміни, підготовка       │ Вибраний день         │
│                                         │ 14:00 Урок фронтенду   │
│ Клік на час / дату → створення           │ 17:00 Заміна           │
│ Клік на запис → деталі                   │                       │
│                                         │ Задачі підготовки      │
│                                         │ □ Підготувати приклад │
│                                         │ [+ Додати на цей день]│
└─────────────────────────────────────────┴───────────────────────┘
```

Це схема розташування, не затверджений макет. Статус Google і його елементи з’являються лише після реалізації інтеграції.

Вигляд:

- Фон `--bg-dark`, поверхні `--bg-card`, поля `--bg-input`, акцент `--primary`; зберегти шрифт програми.
- Заголовок приблизно 22 px, текст 13–14 px, кнопки 32–34 px, іконки 16–19 px.
- Відступи між пов’язаними елементами 6–8 px, між панелями 12–16 px; зовнішні відступи успадкувати від сторінки.
- Основний режим «Тиждень» з часом; «Місяць» для огляду, «Список» для швидкої роботи. Тиждень починається з понеділка, час 24-годинний, українська локалізація.
- Сьогодні та вибраний день мають різні позначення. Тип і джерело запису передаємо також текстом, не лише кольором.
- У місяці показувати кілька коротких записів і кнопку «Ще N». Деталі та довгі назви доступні без розтягування клітинок.
- На вузькому вікні деталі відкриваються поверх календаря або під ним; не стискати три колонки одночасно. Перевірити 900×650, 1280×720, 1440×900 і масштаб Windows 125%/150%.
- Перехід фокуса клавіатурою, Enter для відкриття, Escape для закриття. Перенесення через поле дати доступне поряд із перетягуванням.
- Стани порожнього дня, завантаження, помилки, офлайн і очікування синхронізації мають короткі українські пояснення.

## Поведінка задач і подій

Розрізняємо подію з часом та задачу, яку можна виконати. Типи: «Урок», «Заміна», «Підготовка», «Захід», «Інше». Урок може мати кілька пов’язаних задач підготовки.

Форма першої версії: назва, тип, дата, час за потреби, завершення для події, примітка. Задача може бути без дати; вона доступна у списку «Без дати». Складні повтори, вкладення, теги й розширені чеклісти додавати після базових сценаріїв.

Правила:

- Швидке додавання на вибраний день; збереження показує одразу видимий результат.
- Позначка виконання стосується задачі, а не скасування події чи проведення уроку в Logika.
- Виконані задачі можна приховати й відкрити знову; прострочені задачі зберігаються, доки користувач не виконає або не перенесе їх.
- Перенесення зберігає тривалість події. Якщо API повернуло помилку, повертаємо попереднє положення.
- Видалення спочатку переміщує запис у кошик із можливістю відновлення; зовнішнє видалення має окремий стан синхронізації.
- Для прив’язки до групи використовувати її локальний ID, а для конкретного заняття, якщо він відомий, ID заняття та дату. Назва є підписом, не ключем зв’язку.
- Майбутнє відображення уроків із Logika робити окремим шаром для перегляду. У першій версії джерела уроків: ручне додавання та вибрані Google-календарі. Задачник не запускає синхронізацію чи відправку батьківських звітів.

## Google Календар

### Напрям синхронізації

Узгоджено з користувачем: двостороння синхронізація в окремому календарі «School Manager»; інші вибрані календарі відображаються лише для перегляду. Запис у сторонні календарі до цього плану не входить.

Саме ввімкнення інтеграції не публікує весь локальний список. Користувач вибирає календар і бачить, які записи синхронізуються. Задачі без дати залишаються локальними.

### Підключення акаунта

- Кнопка «Підключити Google» відкриває системний браузер. OAuth Desktop із PKCE і `state`, одноразове повернення через loopback; пароль Google застосунок не отримує.
- Для випуску потрібні Google Cloud-проєкт, увімкнений Calendar API, OAuth client і налаштований consent screen. Публічну перевірку та умови тестового режиму перевірити до розповсюдження.
- Токени зберігати через захищене сховище ОС; API для frontend повертає лише стан підключення й підпис акаунта. Вихід скасовує локальні повтори та прибирає токени, але зберігає локальні задачі.
- Перший реліз підтримує один активний Google-акаунт на профіль застосунку. Ідентифікатор акаунта зберігати у всіх зовнішніх прив’язках.

Це відповідає потоку Google для встановлених застосунків; вхід через вбудований WebView не використовуємо. [OAuth для desktop](https://developers.google.com/identity/protocols/oauth2/native-app).

Права: `calendar.app.created` для окремого календаря застосунку, `calendar.calendarlist.readonly` для вибору календарів, `calendar.events` для створення та редагування подій у календарях, де користувач має право запису. Ідентичність акаунта отримувати через OpenID Connect (`openid email`); жодних прав на Gmail чи Drive. Зберігати стабільний ID акаунта, а email використовувати як підпис. [Дозволи Calendar API](https://developers.google.com/workspace/calendar/api/auth).

### Події та задачі

- Подію синхронізувати з її початком, завершенням, часовим поясом, назвою і приміткою.
- Задачу на весь день представляти як подію на весь день; задачу з часом експортувати з видимою у формі тривалістю, початково 30 хвилин. Це продуктове рішення можна змінити після прототипу.
- «Виконано» є станом задачника. Google Calendar Events не має еквівалентного статусу завершеної задачі; не прирівнювати його до `cancelled`. У керованих подіях можна зберігати власні метадані, а інтеграцію Google Tasks, якщо знадобиться, планувати окремо. [Модель події Google](https://developers.google.com/workspace/calendar/api/v3/reference/events).
- Повторювані події Google відображати разом із винятками та перенесеннями конкретних занять. Створення і масове редагування серій відкласти; не переносити всю серію при зміні одного заняття.
- Одна й та сама подія на двох пристроях чи після повторного входу повинна мати одну прив’язку за ID, а не збігом назви.

### Надійна синхронізація

Локальна база зберігає дані та чергу змін до завершення обміну. Ідентифікація: акаунт + календар + Google event ID; для серій також recurringEventId/originalStartTime. Зберігати revision, etag і стан останньої узгодженої версії.

Після початкового завантаження використовувати incremental sync із `syncToken` і всіма сторінками відповіді. При HTTP 410 перебудовувати лише дзеркало відповідного Google-календаря зі збереженням локальних задач, невідправлених змін і прив’язок. Параметри початкової та наступних вибірок мають бути сумісні. [Синхронізація ресурсів](https://developers.google.com/workspace/calendar/api/guides/sync).

Конфлікт одночасних змін з телефона й застосунку показуємо користувачеві; обидві версії зберігаються до вибору. Скасування зовнішньої події позначаємо явно, пов’язану підготовку не видаляємо мовчки. Повторний запит створення використовує сталий ідентифікатор операції/події.

Початкові інтервали: при відкритті вкладки, відновленні мережі, вручну та раз на 5 хвилин за активного календаря; у треї раз на 15 хвилин. Власні зміни відправляються після збереження через чергу. Ці інтервали виміряти й за потреби скоригувати. Push від Google потребує доступного HTTPS-обробника; окремий сервер у першу desktop-версію не закладаємо. [Push-повідомлення](https://developers.google.com/workspace/calendar/api/guides/push).

HTTP 429/5xx: обмежені повтори зі збільшенням паузи та випадковим зміщенням; після вичерпання спроб видимий стан і ручне повторення. `invalid_grant`: прохання підключити акаунт заново без циклу відкривання браузера. Пропущена синхронізація не блокує локальне редагування.

## Архітектура та дані

План розширюємо поступово, таблиці майбутніх інтеграцій додаємо лише на їхньому етапі.

| Сутність | Основні дані |
| --- | --- |
| `planner_items` | UUID, назва, опис, вид task/event, категорія, статус, дата/час/завершення, all_day, IANA timezone, зв’язок із батьківською подією, revision, created/updated/completed/deleted |
| `planner_connections` | Провайдер, стабільний ID акаунта, підпис, посилання на секрет у сховищі ОС, стан авторизації |
| `planner_calendars` | Провайдер/акаунт/calendar ID, видимість, режим доступу, syncToken, час синхронізації |
| `planner_external_links` | Локальний запис, акаунт/calendar/event ID, etag, дані повтору, остання узгоджена версія |
| `planner_sync_jobs` | ID операції, запис/revision, тип create/update/delete, стан, спроби, наступна спроба, коротка помилка |
| `planner_reminders` | Запис, канал, час UTC, revision, стан, зовнішній ID, ключ захисту від дублів |

Точні моменти зберігати в UTC разом із IANA timezone для відображення. Цілоденні події зберігати календарними датами; не перетворювати їх на умовну UTC-північ. На неоднозначний або неіснуючий час переходу годинника показувати вибір/пояснення.

Орієнтовні нові файли: `frontend/src/pages/TaskPlanner.jsx`, `frontend/src/components/task-planner/`, `frontend/src/styles/task-planner.css`, `backend/task_models.py`, `backend/routers/tasks.py`, `backend/services/planner/`, `tests/test_task_planner*.py`.

Локальний контракт: `/api/tasks` для CRUD, діапазону дат, пошуку й завершення; `/api/planner/google` для стану, підключення, вибору календарів і запуску обміну. Операції приймають revision/ID запиту, щоб повторення не створювало дублів. Віджет надалі використовує цей самий сервіс даних через локальний адаптер із перевіркою доступу.

## Нагадування

### Локальні системні

Після стабілізації календаря додати нагадування на вибраний час через наявний `show_system_notification`, враховуючи загальний перемикач. Для задач без часу користувач вибирає час нагадування явно.

Використати спільний scheduler із власними ID `planner_*`, відновленням із бази після запуску та очищенням лише власних завдань. Після сну показувати одне повідомлення про пропущені нагадування; завершені й скасовані задачі не нагадувати. Повністю закритий процес не гарантує локальні сповіщення; це пояснювати в налаштуванні.

### Telegram, наступний етап

Користувач вмикає особисте нагадування для задачі й обирає дату/час. Відкладене повідомлення в «Збережені повідомлення» підтримується Telegram. Після підтвердженого додавання сервер Telegram виконує заплановане надсилання; закритий застосунок не може змінити або скасувати його до наступного підключення. [Нагадування в Saved Messages](https://telegram.org/blog/scheduled-reminders-themes?setln=uk), [серверна черга](https://core.telegram.org/api/scheduled-messages).

Адаптер використовує ID поточного Telegram-користувача; наявний `send_pyrogram_message` перетворює chat ID на число, тому літерал `me` без адаптації непридатний. Особисті нагадування не додаємо до списку груп батьків або звичайних розсилок.

Зберігати ID акаунта, scheduled message ID і revision задачі. Редагування дати оновлює наявне повідомлення; виконання/видалення скасовує його. Офлайн-скасування має стан «Очікує скасування». Невизначений результат планування спочатку звіряємо з Telegram, без сліпого повторного створення. Завершені технічні записи очищаємо після підтвердження, історію задач залишаємо окремо.

Зміна Google-події запускає перепланування пов’язаного нагадування лише після успішного збереження нової версії. Звичайні помилки задачника не повинні скасовувати завдання автозвітів чи розсилок.

## Віджет Windows 11, майбутній етап

Узгоджено: маленьке вікно із задачами на робочому столі. Для порівняння початкових варіантів:

| Формат | Призначення та наслідки |
| --- | --- |
| Компактне вікно на робочому столі | Найближчий урок, підготовка, позначка виконання, швидке відкриття задачника. Можна досліджувати на основі поточної desktop-оболонки; залежить від запущеного процесу |
| Системний віджет Windows 11 | Інтеграція з панеллю Widgets / Win+W через окремий provider; потребує окремої перевірки пакування й життєвого циклу |

Windows Widgets використовують власний host; для Win32 доступний provider у пакетованому застосунку. Це окремий канал інтерфейсу, а не автоматичне відображення React-сторінки на робочому столі. [Windows Widgets](https://learn.microsoft.com/en-us/windows/apps/design/widgets), [Widget providers](https://learn.microsoft.com/en-us/windows/apps/develop/widgets/widget-providers).

Компактне вікно використовує маршрут `/tasks/widget` та спільну базу задач. Його відкриває desktop-оболонка; окремого інсталятора не потрібно. Залежить від запущеного School Manager.

## Етапи та критерії готовності

| Етап | Результат | Перевірка перед переходом |
| --- | --- | --- |
| 0. Базовий стан | Зафіксовані наявні зміни, копія тестової БД, список критичних сценаріїв | Наявні тести звітів/Logika проходять; виміряно запуск та простій |
| 1. Інтерактивний макет | Окремий демонстраційний екран на вигаданих даних, меню, тиждень/місяць/список, форма | Разом уточнюємо вигляд і сценарії; реальна БД та зовнішні сервіси не використовуються |
| 2. Локальний задачник | Нові таблиці/API, створення, редагування, виконання, перенесення, кошик, робота офлайн | Дані переживають перезапуск, старі таблиці й налаштування збережені, клавіатура й вузьке вікно працюють |
| 3. Google: вхід і читання | Акаунт, список календарів, відображення подій і повторів, локальний кеш | Відмова у доступі, повторний вхід, офлайн, зміна/видалення події та часові пояси обробляються |
| 4. Google: обмін змінами | Узгоджений режим запису, черга, конфлікти, захист від дублів | Зміна з телефона доходить у програму й навпаки; HTTP 410 не знищує локальні задачі |
| 5. Нагадування | Спочатку Windows/macOS, потім Telegram Saved Messages | Перезапуск, сон, зміна дати, виконання, офлайн-скасування та втрачена відповідь без дублювання |
| 6. Windows-віджет | Обраний формат на спільному сервісі даних | Відкриття потрібної задачі, узгоджений стан, окреме вимірювання CPU/RAM і перевірка пакування |

Після кожного етапу показуємо робочу версію, уточнюємо незручності й лише потім розширюємо функціонал. Оцінку часу давати після макета та рішення щодо Google, а не обіцяти наперед для всіх інтеграцій.

## Як захищаємо наявний функціонал

- Реалізуємо погоджений план. Поточні незакомічені зміни звітів, Logika та Telegram зберігаємо.
- Задачник має власні моделі, маршрути, стилі та namespace scheduler. Не змінює `ParentReportLesson`, `ParentReportRun`, правила автозвітів і поведінку накопичених звітів, яку користувач вирішив залишити.
- Бібліотеку календаря завантажуємо лише на вкладці задачника. Немає глобальних перевизначень `.btn`, `.modal`, `.card` чи стилів усіх сторінок.
- Міграції додають таблиці/індекси та є повторюваними. До підключення перевіряємо на копії старої БД; не видаляємо старі таблиці та не запускаємо масового імпорту.
- AuthGate змінюємо точково: доступ до `/tasks` без Telegram та шлях до нього з початкового екрана авторизації. Перепідключення Telegram не повинно закривати незбережену задачу або примусово переводити її на головну. Інші маршрути зберігають чинні правила.
- Усі нові мережеві операції мають тайм-аут і скасування. SQL-транзакції короткі; не тримати запис у SQLite відкритим під час зовнішнього запиту.
- Помилки задачника ізолюються на його сторінці й у worker; журнал українською з ID запису/операції, без токенів, паролів і повного приватного тексту подій.
- Google та Telegram вмикаються незалежно. Вимкнення задачника/його інтеграції не зупиняє scheduler програми цілком.
- EXE у межах планування та прототипу не збираємо.

Перевірки при реалізації: наявний набір `python -m unittest discover -s tests -v`; нові тести даних, часових поясів, синхронізації й нагадувань; frontend build та desktop smoke-test. Візуальна перевірка всіх старих вкладок, входу Telegram, синхронізації груп/Logika, ручного й автоматичного звіту, шаблонів і відкладених повідомлень. Реальні надсилання лише у явно погоджені тестові чати; для задачника надалі погодити окремі тестові нагадування в особисте «Збережене».

Навантаження: підвантажувати лише видимий діапазон календаря, обмежувати список/пошук, прибирати слухачі та скасовувати запити після закриття вкладки. Перевірити багаторазове відкриття, 500–1000 записів, сон/відновлення і простій. Порівнювати CPU/RAM із базовим вимірюванням; не обіцяти відсутність витоків без замірів.

## Рішення, які залишаються для уточнення

- Щільність тижневого календаря й розміщення деталей: праворуч чи у висувній панелі.
- Чи потрібне автоматичне відображення уроків Logika після першої інтеграції Google.
- Відносні нагадування про підготовку, наприклад «за день до уроку», проти фіксованої дати; додати після базових нагадувань.
- Розташування й поведінка компактного вікна після користувацького перегляду.

OAuth-клієнта ще немає: погоджено підготувати інтеграцію та інструкцію `docs/google-calendar-setup.md`. Реальний обмін Google перевіряється після його налаштування; підставні відповіді в тестах не є доказом доступу до живого акаунта.
