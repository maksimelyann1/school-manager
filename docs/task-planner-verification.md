# Перевірка задачника — 27.09.2026

Реалізовано у вихідному коді: вкладка, календар, локальні задачі/події, підготовка до подій, інтеграція Google, особисті нагадування й компактне вікно Windows. EXE не збирався. OAuth-клієнта ще немає: інтеграцію та інструкцію підготовлено відповідно до погодженого обсягу; живий Google-обмін перевіряється після налаштування.

## Вигляд і ресурси

- Переглянуто 1440×900, 1280×720/800, 900×650 та 853×650. Календар переходить в одну колонку; довгі назви скорочуються, повний текст доступний у деталях/підказці.
- Використано емуляцію DPR 1,25/1,5 та відповідні розміри viewport. Системний масштаб Windows не змінювався. Початковий експеримент із CSS `zoom` не використовується як доказ системного DPI: він інакше впливає на вимірювання FullCalendar.
- 20 повних переходів із задачника на іншу сторінку й назад: слухачі 215 → 215, DOM-вузли 743 → 734; JS heap 7,18 → 8,04 МБ після GC. Є початкове кешування; короткий тест не доводить відсутність усіх витоків.
- 1000 записів у SQLite: повертаються перші 500; не більше 6 SQL-запитів. 20 читань під `tracemalloc` — у середньому 169 мс; пік відстежуваних Python-виділень 4,36 МБ, залишок після GC 0,11 МБ. Це не повний RSS процесу.
- 100 проходів обох worker без активної інтеграції/нагадувань: 0,125 с CPU загалом. У програмі вони перевіряються раз на хвилину; зовнішні звернення Google мають власний інтервал і backoff.
- Браузер із 500 синтетичними записами: відображення 168 мс; за 10 с простою TaskDuration зріс на 0,038 с, JS heap — на 632 байти; DOM-вузли й слухачі незмінні. Це локальний замір, не гарантія для всіх комп’ютерів.

## Межі перевірки

- Реальний Google-вхід і двосторонній обмін: після налаштування за `google-calendar-setup.md`; зараз немає OAuth-клієнта.
- Реальні Telegram-нагадування у «Збереженому» не надсилалися; transport у тестах підставний. Живий тест потребує окремої згоди на надсилання.
- Сповіщення ОС перевірені через існуючий адаптер у тестах; доставку конкретним Windows/macOS notification center треба перевірити на встановленій версії.
- Інсталятор, тривалий багатогодинний прогін і реальний DPI різних моніторів не перевірялися. EXE не збирався на прохання користувача.

Робоча база під час перевірок не змінювалася. Одну ранню тимчасову копію БД залишено: автоматична перевірка дозволів заблокувала очищення без докладнішої причини. Наступні копії очищаються штатно після закриття SQLite-з’єднань.

## Відновлення Google Календаря — 12.10.2026

- Реальна причина зупинки: відповідь оновлення OAuth містила зайвий `id_token`.
  Запис займав 3292 байти UTF-16, Windows повертав `CredWrite`, код 1783.
  Після відбору потрібних полів — 1364 байти; запис/читання у тимчасовому
  захищеному записі Windows успішні. Робочий токен не підмінявся тестовим.
- На тимчасовій копії робочої SQLite-бази виконано реальні GET-запити до
  чотирьох календарів. Синхронізація завершилась `connected`; збережено 363
  записи, календарний запит на найближчі 28 днів повернув 16 подій.
  Будь-які записи у Google блокувалися тестовим адаптером.
- Після шести тимчасових збоїв зберігається backoff до приблизно години,
  після нього програма повторює синхронізацію. Відкликаний доступ залишається
  зупиненим до повторної авторизації. Ручна кнопка обходить backoff.
- Відтворено падіння React при скасуванні читання JSON: клієнт повертав `{}`,
  а календар отримував `items=undefined`. Скасування тепер залишається
  `AbortError`; запізнілі й некоректні відповіді не замінюють поточні події.
- Браузер 1280×750: відновлення з помилки, створення серії з трьох повторень
  у вибраному календарі, редагування лише назви, імпорт віддаленої зміни,
  видалення серії, календар лише для перегляду, приховування/показ календаря,
  двадцять подій повернення фокуса та повторні ручні синхронізації — успішно.
- Повний Python-прогін: 169 тестів успішно; після уточнення діагностики —
  8 тестів відновлення успішно. Окремо 5 перевірок API-клієнта Node успішно.
  Фронтенд зібрано. Інсталятор/EXE не збирався.

Реальні створення, зміни, видалення подій та запрошення гостей у Google
під час цієї перевірки не виконувались: їх перевіряли на підставному API.
Робочі бази й календарні дані користувача не змінювалися.
